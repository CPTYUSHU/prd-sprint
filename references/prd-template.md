# PRD 模板 & 写作规范

> AI 生成 PRD 时按此模板结构输出。生成时删除所有 `<!-- 注释 -->`，只保留实际内容。

---

## 输出格式

```markdown
# {功能名称} PRD

> {产品名} {功能名称}功能需求文档
> 版本：v1.0 | 日期：{YYYY-MM-DD} | 状态：初稿
```

---

## 章节结构 & 写作规范

### 1. 概述

```markdown
## 1. 概述

**一句话**：{动词开头，不超过 40 字，说清做什么、给谁、解决什么}

**背景**：
- {业务背景 1}
- {业务背景 2}

**目标**：
1. {可衡量的目标}
2. ...

**范围外（本期不做）**：
- {明确排除的功能}
```

<!-- 规范：
- 背景 2-3 条，每条一句话
- 目标不超过 3 条，每条能回答"怎么验证做到了"
- 范围外必须列出讨论过但不做的内容
-->

### 2. 用户故事

```markdown
| 编号 | 角色 | 故事 | 优先级 |
|------|------|------|--------|
| US-01 | {具体角色} | 我想{做什么}，以便{价值} | P0 |
```

<!-- 规范：
- 角色要具体：写"普通用户"/"运营人员"，不写"用户"
- P0 = 必须有 / P1 = 应该有 / P2 = 锦上添花
-->

### 3. 功能清单

按端拆分子章节（3.1 用户端、3.2 管理后台等），每端一张表：

```markdown
### 3.1 {端名称}（{技术栈}）

| 功能 | 描述 | 优先级 |
|------|------|--------|
| {动词开头} | {具体描述} | P0 |
```

<!-- 规范：
- 功能名动词开头："展示"/"支持"/"管理"/"查询"
- 描述具体到交互细节，不写"详见设计稿"
-->

### 4. 用户流程

每个核心流程一个 Mermaid flowchart：

```markdown
### 4.1 {流程名称}

​```mermaid
flowchart TD
    A[起点] --> B[步骤]
    B --> C{判断}
    C -->|条件1| D[结果1]
    C -->|条件2| E[结果2]
​```
```

<!-- 规范：
- 用 flowchart TD（自上而下）
- 判断节点用 {菱形}
- 节点文字不超过 15 字
- 至少覆盖：主业务流程 + 管理端流程
- 成功和失败路径都要画
-->

### 5. 页面说明

按页面拆分，每个页面包含**布局说明**和**交互逻辑**两部分：

```markdown
### 5.1 {页面名称}

- **入口**：从哪进入
- **布局**：
  - {区域 1}：描述
  - {区域 2}：描述
- **交互逻辑**：
  - {逻辑 1}：条件判断、状态流转、权限差异等
  - {逻辑 2}：数据来源、联动规则、边界处理等
```

<!-- 规范：
- 说清入口在哪
- 「布局」描述页面有哪些区域和元素
- 「交互逻辑」描述关键的业务规则和状态流转，例如：
  - 筛选条件之间的逻辑关系（AND/OR）
  - 数据刷新策略（实时 vs 定时）
  - 不同角色看到的差异
  - 操作的前置条件和后置影响
  - 空状态、加载状态的处理
- ≤4 页时用并排卡片式排版（HTML 输出）
- >4 页时每个页面独立章节全宽展开，给交互逻辑足够的展开空间
-->

### 6. 交互规格

按模块列出所有用户可操作的交互点。每个交互写清完整的 **触发 → 处理 → 结果** 链路，让开发不用猜：

```markdown
### 6.1 {模块名}

**{操作名称}**
- 触发：{用户做了什么，如"点击兑换按钮"}
- 前置条件：{什么条件下可操作；不满足时按钮状态/提示}
- 处理：{前端行为 + 后端逻辑，如"调用 POST /api/exchange，扣减积分，生成订单"}
- 成功：{UI 怎么变 + 数据怎么变，如"Toast 提示，积分余额更新，跳转订单详情"}
- 失败：{各场景的具体提示，如"积分不足 → Toast「积分不足，还差 N 积分」"}
- 补充：{防重复点击、loading 态、并发限制、权限要求等}
```

<!-- 规范：
- 按功能模块分组（如"客户管理"、"消息中心"），不按页面分
- 覆盖所有 P0/P1 功能的用户操作，P2 可简写
- 每个操作必须包含：触发、前置条件、成功、失败，"处理"和"补充"按需写
- 失败场景要具体到提示文案，不写"提示错误信息"
- 涉及数据变更的操作必须说明：改了哪张表的什么字段、是否需要回滚
- 涉及权限差异的操作必须标注：哪些角色可以操作
- 与「页面说明」的交互逻辑互补：页面说明侧重"页面长什么样、规则是什么"，交互规格侧重"每个操作点下去会发生什么"
-->

### 7. 数据 & 字段说明

每张表一个子章节：

```markdown
### 6.1 {中文表名}（{english_table_name}）

| 字段名 | 类型 | 必填 | 校验规则 | 示例值 |
|--------|------|------|----------|--------|
| `field_name` | VARCHAR(100) | 是 | 1-100字符 | "真实示例" |
```

<!-- 规范：
- 字段名英文 snake_case，用 `code` 格式
- 类型具体：VARCHAR(100)，不写 STRING
- 必填：是 / 否 / 条件必填（注明条件）
- 校验规则具体："> 0"，不写"正数"
- 示例值用真实业务数据
- 每表都要有 id、created_at
- 关联关系注明"关联XX表"
-->

### 8. 异常流程 & 边界情况

```markdown
| 场景 | 处理方式 |
|------|---------|
| {场景} | {具体处理：用户看到什么、数据怎么处理} |
```

<!-- 规范：
- 从主流程每个判断节点反推异常
- 必须覆盖：并发、超时、数据不一致、权限、网络异常
- 处理方式到具体提示文案和数据回滚逻辑
- 历史 bug 特别标注
-->

### 9. 验收标准

按端/模块分组，每条格式：

```markdown
### {分组名}

| 编号 | 验收条件 |
|------|---------|
| AC-01 | {主语} + {操作} + {可量化的预期结果} |
```

<!-- 规范：
- 每条可测试："1秒内响应"，不写"响应要快"
- 包含性能指标
- 覆盖所有 P0 功能点
-->

### 10. 待确认事项

```markdown
| 编号 | 问题 | 关联方 |
|------|------|--------|
| TBD-01 | {具体问题，可附带建议方案} | {角色} |
```

### 技术备注（末尾）

```markdown
## 技术备注

- 现有接口：`GET /api/xxx`
- 后端技术栈：{框架}
- 前端技术栈：{框架}
- 第三方依赖：{服务}
- 技术风险：{需评审讨论的点}
```
